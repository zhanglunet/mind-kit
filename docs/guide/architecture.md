# 系统如何运作

> 一句话:**原始来源只读、LLM 编译成互联 Wiki、人从 Wiki 调用**;代码与内容分两个仓,
> 四道确定性门禁防止规模化后腐化。
>
> 可视化版本见文档站的[系统运作](architecture.html)页(本文是文字版,内容一致)。

## 0. 四层一图:一篇文章怎么变成可调用的知识

下面各节分头讲权责、布局、流水线与门禁;这一张先把**数据怎么流**说完。

```
来源层     raw/clippings   raw/flomo/delta   raw/pdfs        raw/todo
RAW · 只读       └──────────────┴──────────────┘                │
唯一真相         三者都在 config.yaml 的 sources 里      只有这个走人工深度处理
                                │                               │
               ┌────────────────┴─────┐      ┌──────────────────┴─────┐
加工层         │ ① sage-wiki compile  │      │ ② LLM 对话式 ingest    │
两条路         │    引擎自动,批量     │      │    人在环,先讨论再抽取 │
               └───────────┬──────────┘      └────────────┬───────────┘
                           │                              │
─────────────────────────────────────────────────────────────────────────
知识层     ┌───────────────▼──────────────┐  ┌────────────▼────────────┐
_wiki/ +   │ 引擎领地(LLM 只读)          │  │ LLM 领地                │
material/  │ summaries · concepts ·       │  │ outputs/ · material/ ·  │
内容库·私有│ entities                     │  │ reports/                │
           └──────────────────────────────┘  └─────────────────────────┘
             门禁:OKF 体检                     门禁:写集校验 · 决策队列 · 保鲜
─────────────────────────────────────────────────────────────────────────
调用层      index.md 导航   本地浏览站   ① 本地检索(秒级,不走 LLM)
人                                        ② 引擎查询(数十秒,带来源引用)
                                                     │
                    有价值的产出 ─────回流────────────┘
                    写回 outputs/ 并记一条 log(让探索也复利)
```

三件事这张图说得比文字清楚:

- **两条加工路,不是一条。** 剪藏走引擎批量编译;重要文章走对话式 ingest(先讨论再抽取),
  两者落在**不同领地**,权限也不同——这是第 1 节三条红线的由来。
- **门禁挂在写入点上,不是挂在嘴上。** 引擎领地由 OKF 体检把关,LLM 领地由写集校验、
  决策队列、保鲜三道把关;都是脚本,不是提示词(第 4 节)。
- **调用层有一条回流箭头。** 查询产出不是聊完就散,有价值的写回 `outputs/`——
  这条回流才是"知识复利"的实现,没有它就只是个搜索引擎。

## 1. 三层架构:谁能写什么

系统不漂移的关键,是把"谁能改哪些文件"写成可版本化的 Schema(`CLAUDE.md`),而不是靠约定俗成。

```
┌─────────────────────────────────────────────────────────┐
│  第三层 · Schema(CLAUDE.md)                             │
│  系统"宪法":规定各角色权责边界、目录规范、工作流         │
└───────────────────────┬─────────────────────────────────┘
                        │ 约束下面两层
        ┌───────────────┴───────────────┐
        ▼                               ▼
┌───────────────────────┐   ┌───────────────────────────┐
│ 第一层 · Raw(raw/)   │   │ 第二层 · Wiki(_wiki/)     │
│ 剪藏 / PDF / 笔记导出 │──▶│ summaries · concepts ·    │
│ **只读,唯一真相**     │编译│ entities(引擎领地,LLM 只读)│
└───────────────────────┘   │ outputs/(LLM 产出)        │
                            └─────────────┬─────────────┘
                                          │ 调用
                                          ▼
                            人:选题 / 提问 / 写作 / 决策
```

**三条红线**:

1. `_wiki/summaries|concepts|entities` 是**编译引擎的领地**,LLM 只读;产出写到 `_wiki/outputs/`
2. 原始来源**只读不写**;笔记类原始导出永不修改,只编译其增量目录
3. 处理完的 `todo` 移入 `archive/`,不回 `clippings/`(否则重复编译)

## 2. 双库布局:代码与内容分离

**代码库不含任何个人内容。** 知识内容在**另一个私有仓**,经符号链接挂进同一个工作目录:

```
second-brain/
├── mind-kit/                    ← 代码库(工具、脚本、文档)
│   ├── scripts/ tests/ docs/ prompts/ evaluation/   ← 真实文件
│   └── _wiki  material  raw  writing  reports/…     ← 全是软链 ↓
│
└── mind-vault/                    ← 你的内容库(私有)
    └── _wiki/ material/ raw/ writing/ reports/      ← 个人内容本体
```

由此产生两条硬约束:

- 克隆代码库后**不会有** `_wiki/`、`material/`、`raw/` —— 这是设计如此,跑 `scripts/init-vault.sh` 建自己的
- 提交个人内容一律走 `scripts/vault.sh commit`(唯一漏斗,带写集校验门禁),**不要**在代码库里 `git add` 个人目录

## 3. 编译流水线:一条命令走完

`scripts/compile.sh` 把七件事串成一条命令:

```
raw/clippings/ 新增文章
        │
        ▼
  ① sage-wiki compile      来源 → summaries / concepts / entities
        ▼
  ② build-index.py         重建 _wiki/index.md 导航
        ▼
  ③ sage-wiki lint         健检:矛盾 / 孤立页 / 缺失交叉引用 → 记账到 reports/lint/
        ▼
  ④ freshness.py           保鲜复核:按半衰期列出"该复核"的页(只提示,不改)
        ▼
  ⑤ decision.py check      决策队列状态机不变量校验
        ▼
  ⑥ build-wiki-site.py     生成本地浏览站 browse/wiki/(含关系图)
        ▼
  ⑦ vault.sh commit        产物提交到内容库 ← 此处过**写集校验门禁**
```

更外层还有 `scripts/update-all.sh`:日报 → `compile.sh` → 订阅台账 → 门户 → 文档站。
三条路触发同一个脚本 —— **命令行 / 网页按钮 / 定时自启**。

## 4. 四道机器:让它规模化不腐化

知识库越大越怕漂移与静默腐化。除理念外,系统落了四道**确定性可执行**的机制 ——
不是提示词里的软约束,而是脚本、测试与门禁。

| | 机制 | 做什么 | 关键设计 |
|---|---|---|---|
| **E1** | 本地检索栈 `searchlib.py` | BM25 + CJK bigram 分词 + RRF 三通道融合 + 双语同义扩展 | 秒级、**不走 LLM**;索引按输入指纹**自动失效重建** |
| **E2** | 评测与回归 `evaluation/` | 检索 golden case(MRR / Top-1)+ 质量 required/forbidden token 断言 | **基线只增不减**;锁住"认知边界"而非只测召回 |
| **E3** | 决策队列 + 保鲜 | 须先确认的动作走状态机;重要页按半衰期提示复核 | **审批与执行分离**;保鲜**只提示不擅改** |
| **E4** | 写集校验 `validate_write_set.py` | 提交前对**变更页**跑确定性校验 | 只校本次写集(不扫全库);坏页拦在入库前,带逃生舱 |

**为什么是"机器"而不是"规范"**:`CLAUDE.md` 里写着一条原则——
> 只有脚本/测试能确定性执行的规则才算硬门禁;提示词与文档条款只是尽力遵守的软规范。
> 想让某条规范"必须遵守",就为它写可执行检查,别指望文字自我执行。

## 5. 查询:两条路

```
                      ┌──────────────────────────────┐
  问题 ──────────────▶│ ① 本地检索 /api/search        │ 秒级,不走 LLM
                      │   BM25+bigram+RRF+同义扩展    │ 适合"找页面"
                      └──────────────────────────────┘
                      ┌──────────────────────────────┐
                 └───▶│ ② 引擎查询 /api/query         │ 数十秒,走 LLM
                      │   综合多页 + 带来源引用       │ 适合"要答案"
                      └──────────────┬───────────────┘
                                     ▼
                       有价值的产出 → _wiki/outputs/ 并记一条 log
                       (让探索也复利,不让洞见死在聊天记录里)
```

本地服务 `scripts/brain-server.py` **只绑回环地址**,提供门户页与这两个 API。

## 6. 隐私边界:什么永不上网

```
        ┌──────────────── 公开 ────────────────┐
        │  site/          文档站(部署到公网)   │
        │  scripts/ tests/ docs/ prompts/      │
        └──────────────────────────────────────┘
        ┌──────────────── 私有 ────────────────┐
        │  raw/ _wiki/ material/ writing/      │  ← 内容库,永不进代码库
        │  browse/        本地浏览站(gitignore)│
        │  raw/private/   冷存层,永不读写入库  │
        └──────────────────────────────────────┘
```

代码库有一道**可执行门禁**(`tests/test_no_personal_identifiers.py`)防止个人标识回流:
用**形状匹配**(如 `ou_` + 24 位 hex)而非字面值 —— 把真实标识写进测试文件,等于泄露仍在库里。

## 7. 运行时:两端如何分工

前面各节讲的是**数据怎么流**;这一节讲**谁在什么时候跑**。

```
  编辑端(笔记本)                git 两个仓                服务器端(7×24)
  ─────────────────            ─────────────            ────────────────────
  人在这里:                                              定时编排(每日一次)
   · Obsidian 读写库             代码库                    └ update-all.sh 七步
   · Web Clipper 剪藏      ◀── 只 pull ───┐                   ① 拉内容库  ·核心
   · vault.sh commit                      │                   ② 日报
   · 改 docs/ 才重建文档站                │                   ③ 编译      ·核心
                                          │                   ④ 推内容库  ·核心
  每日只做两件事:                内容库   │                   ⑤ 订阅台账
   · pull 内容库             ◀── 双向 ───┤                   ⑥ 门户入口
   · pull 代码库                          │                   ⑦ 文档站(本端跳过)
                                          │
  **不跑编译**                            │                常驻服务(systemd)
  (锁只锁同机,跨机没有锁                │                 · 本地门户 · 回环地址
   两边同时编译必冲突)                   │                 · 对话入口 · 长连接出站
                                          │                 每日一次异地备份
  ────────────────────────────────────────┴──────────────────────────────────
  对外只有两个出口:
   · 文档站 ← 从代码库 main 的 site/ 部署(生成物入库,故只在编辑端重建)
   · 公开发布仓 ← publish-kit.sh,过三道门禁(禁忌词 / 公开树测试 / 世系新鲜度)
  本地门户只绑回环地址,要看走 SSH 隧道 —— 不开任何入站端口。
```

三条约定值得单独说:

- **编译只在服务器端跑。** `.update-all.lock` 只锁同机进程,**跨机器没有锁**。
  两端同时编译再各自 push,内容库必然冲突。所以编辑端的定时任务只剩 pull。
- **文档站只在编辑端重建。** `site/*.html` 是**提交进仓的生成物**(文档站从
  代码库 main 的 `site/` 部署),而不同机器的 pandoc 版本会渲染出不同 HTML ——
  谁跑谁把代码仓弄脏。服务器端设 `MIND_BUILD_SITE=0` 跳过这一步,
  跳过理由会如实打印,不会伪装成「缺 pandoc」。
- **失败要能被看见。** 七步里三步标了 `·核心`:缺工具时**判失败而不是跳过**,
  否则 cron 天天报绿而 Wiki 悄悄停摆。
  <br>编译内部同理:建索引与 lint 挂掉**不中止**(中止会丢掉本轮产物),
  但会记账并在末尾非零退出;而保鲜/决策/OKF 体检这类**记账**步骤仍是 best-effort ——
  它们报的是内容发现,不是基础设施故障。
  <br>⚠️ 已知缺口:整体退出码目前**没有消费者** —— cron 把输出重定向进日志,
  失败只体现在日志文本里,没有告警。这条如实记着,还没修。

## 8. 开发与发布

开发纪律遵循 [Superpowers](https://github.com/obra/superpowers):**测试先行 · 系统化优于拍脑袋 ·
简单为第一目标 · 用证据而非声称**。硬约束:

- **脚本改动强制 pytest-first**:先写会失败的测试(RED)→ 实现到通过(GREEN)→ 重构
- **pre-push 钩子**跑全量 pytest,红则拦;GitHub Actions 服务端兜底
- 收尾必**真跑一遍留证据**,而非"应该没问题"
